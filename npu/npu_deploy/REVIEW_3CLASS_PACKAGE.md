# 对 `dcdc_npu_threeclass_image_20261027_v2` 的独立审查

审查时间：2026-10-27。审查者只用了包内文件 + 我自己的工具链，**没有**依赖他们的脚本或二进制。

## 一、先说结论

**这是一个设计合理、文档诚实的交付包；模型本身我独立复算过，是自洽的。**
但有三处会挡住"别人接手就能复现"：包里没有可执行文件、板端证据是截图不是日志、
`baseline_f64.bin` 的语义对不上他们自己的 FP32 说明。

## 二、我独立验证通过的部分

| 检查 | 方法 | 结果 |
| --- | --- | --- |
| 模型完整性 | sha256 vs `model_contract.json` | ✅ `5f78559d…60c7` 一致 |
| 量化参数一致性 | 契约 vs 图上 `s0/z0` 初始化器 | ✅ scale=0.0405944586、zp=163 完全相同 |
| 图结构 | 我自己写的 ONNX 解析器 | ✅ 11 个节点：DQ→Conv3x3(pad1,16ch)→Q→DQ→Relu→Q→DQ→MaxPool2x2→Q，输入 `[1,3,16,16]` u8、输出 `[1,16,8,8]` u8，与文档描述一致 |
| **数值可复现** | 用**我自己的** numpy 解释器 + 他们的 `input_u8.bin` 跑，对 `features_u8.bin` | ✅ **46/46 例完全一致，最大 0 码差**（比他们板端 ≤2 码还好） |
| 预处理/量化链 | `input_f32.bin` 按契约量化 vs `input_u8.bin` | ✅ 46/46 完全相等 |
| 未用通道清零 | 通道 3..15 的 max | ✅ 恒为 0，符合契约 |
| 类别正确性（该样本库） | 我复算的类别 vs `cases.txt` 标签 | ✅ 46/46 |

> 说明：`features_u8` 能在我的解释器上 0 码复现，等于证明了「模型 + 量化参数 + 前后处理契约」
> 三者是自洽的；他们板端的 2 码差是 NPU 实现层面的舍入，不是模型文件的问题。

## 三、我发现的三个问题

1. **包内没有可执行文件，因此包内没有可复现的板端证据。**
   README 明确说了没放二进制（诚实），但这意味着：拿到包的人必须有一台装了
   `aarch64-linux-gnu-g++` 的 Ubuntu，而板端结果只剩用户截图。
   `board_execution_status.json` 里引用的两张 `codex-clipboard-*.png` **不在包内**。
   → 我用 Windows 上的裸机 gcc 12 + SDK sysroot 把他们的 `src/main_threeclass.cpp`
   编出来了（`work/_build/their_3class_infer`，147 KB，aarch64 动态 ELF），
   所以这个缺口是可以补上的：**不需要 Ubuntu 也能编译**。

2. **`vectors/*.baseline_f64.bin` 的语义对不上他们自己的 FP32 说明。**
   `fp32_checkpoint_validation.json` 说 FP32 的 top1-top2 间隔中位数约 0.5、准确率 1.0；
   而这些 bin 里的数值量级是 47.9 / 0.52 / 0.67 这种，用它做 argmax 只有 **67.4%** 命中标签。
   两种可能：它不是 FP32 logits（可能是物理量/旧版模型输出），或者类顺序与契约不同。
   → 建议：要么在 README 里写清它是什么、怎么生成，要么直接删掉，别让人误当参考。

3. **类别极不均衡，且振荡类没有独立验证。**
   训练窗口数 `9513 / 135 / 2692`（transient 只有 135 个，类别权重 30.5），
   他们自己也写了"振荡样例来自两组参与训练的 PLECS run"。
   我的复算也复现了这一点：这 46 例里 30 例是 train 集。
   → 46/46 只能说明"链路通 + 这批样本不难"，不能当作三分类泛化证据。

## 四、和已有四分类成果的关系

|  | 这个包（三分类） | 我这边（四分类） |
| --- | --- | --- |
| 任务 | normal / load_transient / oscillation | 轻载 / 额定 / 近限流 / 保护故障 |
| 输入 | 3×16×16 = 2 s 历史窗（过去相对特征） | 单窗口 3 特征（V/I/duty） |
| 板端证据 | 优化图含 ALHardNPU（说法），日志未随包 | **IRQ 41 计数 615 次 + 0.160 ms vs CpuRef 5.098 ms** |
| 可复现性 | 需 Ubuntu 编译；二进制未提供 | 一条命令重跑，二进制已就绪 |

两者互补：他们的特征工程（过去相对 + 2 s 窗）更贴近赛题的"瞬态/振荡"，
我的部署与取证链路（交叉编译、IRQ 计数、概率级对拍）更完整。

**一个值得注意的矛盾点**：他们的图里 ReLU 作用在 **float** 上，中间还夹着 MaxPool，
按我之前的实验（8 通道、Relu 夹在 Conv 和 Q 之间）这种结构不该融合，
但他们声称融合出了 ALHardNPU。两种解释：融合对**通道数（16 vs 8）**更敏感，而不是对 ReLU 位置；
或者他们的融合结论只在那一个样例上成立。**这一条等板子回来我会用他们的模型 + 我的
`--optimize-only` + IRQ 计数直接验一遍**，结论会写进 `BOARD_FINDINGS.md`。

## 五、建议他们补的三件事

1. 把 `dcdc_npu_threeclass_infer` 的 aarch64 二进制放进 `bin/`（或接受我这份用裸机 gcc 编的），
   并附上代表性样例的 `optimized.dot` 与 `profile.json`，让 ALHardNPU 的结论可核查。
2. `baseline_f64.bin` 要么写清语义，要么删。
3. 报 per-class recall（尤其 transient，只有 135 个训练窗口），并补一组**未参与训练**的振荡数据。
